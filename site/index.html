What if your next onboarding guide became something people could actually practise? Turn an idea into a hands-on GitHub exercise, with GitHub Copilot and the gh-skills-builder plugin.

For educators, maintainers, enterprises, startups, and internal training, this workshop puts you in the architect's seat. Copilot helps draft the content and scaffold the files. You shape the learning experience.

One orchestrator agent and five reusable skills guide the journey: outline, bootstrap, review, publish, and orchestrate the whole loop. Install the plugin from the awesome-copilot marketplace in the Copilot app or CLI.

Start with the outcome. Define what learners will practise, what success looks like, and how to check it. Then turn the approved outline into a runnable, issue-driven GitHub Skills exercise.

The example uses Tailspin Toys to teach three practical Copilot habits: clear repository instructions, consistent quality reports, and a report-only QA agent. A small exercise, with a concrete purpose.

Checks examine what learners wrote, not just whether a file exists. Review the findings, approve a targeted fix, and review again. Useful feedback helps learners understand what to improve.

People stay in control of the decisions. Prepare the validation evidence and launch checklist, then pause. Release readiness is not permission to publish, and this workshop stops before public release.

Watch the live walkthrough, then replay the copyable prompts at your own pace. The website brings the slides, instructions and resources together. Repeatable, observable, inclusive, and human-led.

Explore the workshop, get the plugin, and bring your next idea. Build a learning experience people can put into practice.

What is a plugin?

An installable toolkit that adds reusable capabilities to GitHub Copilot.

+ gh-skills-builder

Install once.
Reuse the workflow.

A

One agent

@github-skills-orchestrator coordinates the work and asks for your approval.

S

Five skills

Reusable workflows and capabilities the agent loads, one for each phase plus one to run the whole loop.

A plugin packages customizations. It is not a separate AI model.

Add the toolkit. Start building.

gh-skills-builder is available in the Awesome Copilot marketplace.

  1. Find it

    Open Plugins in the Copilot app. Find gh-skills-builder.

  2. Review + install

    Review the source and capabilities. Install and enable it for your session.

  3. Use it

    Choose the orchestrator agent. Ask it to run the exercise lifecycle.

Prefer the CLI?

Install

copilot plugin install gh-skills-builder@awesome-copilot

If the CLI says the marketplace is unknown, register it once, then rerun the install

copilot plugin marketplace add github/awesome-copilot

Confirm the install

copilot plugin list

@github-skills-orchestrator is the agent; the slash commands are skills. Install gh-skills-builder 3.0.0 or later: earlier releases use different skill names than the prompts on this page.

Today's scenario: Tailspin Toys

Build a 15–20-minute Copilot quick-start inside Tailspin Toys.

1

Start with a real app

Tailspin Toys as MIT starter code. Learners customize Copilot, not app features.

2

Teach three habits

Repository instructions. Consistent quality reports. A report-only QA agent.

Working title: Copilot app Cleared for Takeoff.

The three graded learner steps
Learner stepArtifactWhat validation can observe
1. Add a TypeScript documentation convention.github/copilot-instructions.mdA new, clearly delimited workshop section requires TSDoc for new or changed exported TypeScript functions, preserving existing instructions.
2. Make quality reporting consistent.github/skills/quality-checks/SKILL.mdThe existing skill keeps its frontmatter and gains a reporting contract: command, passed/failed/blocked status, evidence, and the reason for any failed or blocked check. No invented results.
3. Define a report-only QA agent.github/agents/qa.agent.mdValid name and description frontmatter, plus instructions to report requirements with evidence, ask before implementation changes, and never commit or open PRs.

Validation checks what each learner wrote, not just whether a file exists, and not whether they invoked Copilot.

One agent. Five skills. Four phases.

One coordinator loads the capability needed for each stage. The skills do the work; people decide when to advance.

  1. 01

    Outline

    Decide what success looks like: outcome, identity, and what a workflow can actually check.

    /github-skills-outline
  2. 02

    Bootstrap

    Make the outline runnable: README, step files, and workflows in the current repository.

    /github-skills-bootstrap
  3. 03

    Review

    Report findings without editing. Approve one fix, then review again.

    /github-skills-review

Sessions and modes

Use one quick chat for Prompt 1, Gate 1, and the Hand-off Authorization. Then use one project session, opened on the new repository, for Prompts 2–4.

  • Mode: Interactive throughout, so you stay in the approval loop.
  • Model: Auto → Intelligence for the outline quick chat; Auto → Balance for the project session, if those controls are available.

Interactive is not a security boundary. Tool permissions and explicit authorization still matter.

01 Outline and hand-off Quick chat

Prompt 1 · Create the outline

@github-skills-orchestrator Use /github-skills-outline to design a
15–20-minute GitHub Skills exercise for a new Tailspin Toys teammate.

Keep exactly three graded learner steps:
1. Add a clearly delimited workshop section to .github/copilot-instructions.md
   requiring TSDoc for new or changed exported TypeScript functions. Preserve
   existing instructions.
2. Customize .github/skills/quality-checks/SKILL.md so reports include
   command, passed/failed/blocked status, evidence, and reasons for failed or
   blocked checks. Preserve frontmatter. Never invent command results.
3. Create .github/agents/qa.agent.md with name and description frontmatter. It
   reports requirements with evidence, asks before implementation changes, and
   never commits or opens PRs.

For each step include a short Theory block, one Activity, success criteria, a
repository-observable validation signal, and useful failure feedback. Validate
the content of learner artifacts, not just file existence. Do not claim
Actions can prove which local app mode or agent was used.

This is a small slice of the Dev Days Copilot app scenario, not a conversion
of the full lab. Do not add filtering, application changes, dependency
installation, database setup, browser tests, feature PR/merge requirements, or
extra graded steps. Mention Agent Merge, MCP, and canvases only as optional
next steps.

Propose a title and three lowercase-hyphenated repository names containing
copilot-app, without a skills- prefix. Recommend one.

We are in a quick chat with no repository. After I approve the identity and
outline, return the complete standalone exercise-outline.md content in one
Markdown code block. Start with # <approved title>, then Repository name:
<approved name>, then Learner copy: skills-<approved name>. Do not claim a
file has been saved.

Gate 1 · Approve the outline and identity

Approved. Use "Copilot app Cleared for Takeoff" and repository name
copilot-app-cleared-for-takeoff. Keep exactly the three approved learner
steps. Return the complete outline artifact in one Markdown code block,
including the title, Repository name, and Learner copy header. Do not create a
repository or claim to have saved a file.

Hand-off Authorization · Create the private authoring repo

Hand-off Authorization: I authorize running this existing workshop script once
to create my private authoring repository, import the Tailspin starter code,
commit, and push. This is not permission to publish a public template or run
the exercise lifecycle.

<workshop-repo>/handoff.sh <you> copilot-app-cleared-for-takeoff

Show the output and local folder path. Do not create other repositories or
files beyond the script's work.

Or run the hand-off yourself in a terminal

<workshop-repo>/handoff.sh <you> copilot-app-cleared-for-takeoff

02 Bootstrap Project session

Prompt 2 · Build the exercise

@github-skills-orchestrator Phase I is approved. Use
/github-skills-bootstrap with this outline artifact:

<paste the approved outline artifact>

First save that artifact verbatim to .github/exercise-outline.md. Use its
identity header for the README and Copy Exercise badge. Stop and ask if its
repository name differs from this repo.

Build exactly three graded steps plus the standard completion/review material.
Preserve Tailspin's MIT LICENSE and credit github-samples/tailspin-toys in the
README.

Do not complete the learner tasks: leave the new TSDoc workshop section, the
quality-reporting contract, and qa.agent.md for the learner to add. Inspect
the existing starter files first so validation requires a meaningful learner
change instead of passing the baseline.

Step 0 opens the normal exercise instructions issue only; do not seed any
other issues. Keep existing Tailspin workflows intact, but do not depend on
their checks for exercise progression.

Use lightweight artifact checks for all three steps. Do not run or require npm
ci, app builds, database setup, Playwright, or application tests. Check
frontmatter and required reporting/behavioral instructions with helpful
failure feedback, not file-exists or arbitrary whole-file text matching alone.

Follow the GitHub Skills workflow contract, use scoped permissions, and
inspect workflow event/path interactions. Report what was actually validated
and what remains untested. Do not publish or create another repository.

Gate 2 · Accept the build

I accept this build round. Do not make more changes. I will send the
report-only review request next.

03 Review Same project session

Prompt 3 · Report-only review

@github-skills-orchestrator Use /github-skills-review. Report
findings without editing files.

Check the approved three-step scope, learner clarity and accessibility,
workflow safety, and validation reliability. In particular:
- The untouched starter must not already pass the three learner checks.
- Each correct learner artifact should pass; an incomplete or incorrect
  artifact should fail with useful feedback. Inspect and, where feasible,
  exercise those cases.
- Step 0 must open only the exercise instructions issue and create no other
  issues.
- No grade should depend on npm, an app build, browser tooling, or proof that
  the learner used a local Copilot mode.
- Repository-observable checks of written policies must not be described as
  proof of model behavior.

Prioritize actual release blockers and include evidence and untested risks. If
no findings are supported, say so; do not invent a finding for the demo.

Prompt 3a (optional) · Preview README and all steps in a browser canvas

Show the current exercise README.md and all .github/steps/*.md files in a
browser canvas for a read-only learner-experience review.

Render the full Markdown, not summaries or source code. Put the README first,
then every numbered step in numeric order, then x-review.md. Include any
other step Markdown files in the navigation. Label each page with its source
path and provide a table of contents plus previous/next navigation. Preserve
headings, ordered lists, code blocks, links, images, details blocks, and
GitHub-style callouts so we can inspect readability and the learner journey.
Clearly label unresolved template variables as an unrendered preview; do not
invent their values or claim this is the live issue experience.

Keep all exercise files unchanged. If a local preview needs generated files,
use a temporary directory outside the repository and bind any server to
loopback only. Do not upload private content to an external renderer.
Do not run workflows, click Copy Exercise, create repositories, or publish.
If a source file or browser canvas is unavailable, report it explicitly.

Keep this read-only visual pass within the review time box. It previews the exercise Markdown, not the Tailspin app, and does not replace workflow checks or fresh-copy testing. Skip it if time is tight or the canvas is unavailable.

Prompt 3b (optional) · Approve one fix

I approve a bootstrap fix round for <finding-id> only. Make the targeted fix
and run its relevant checks. Stop for my build approval before running the
review again.

Accept the fix and review again

I accept the fix round. Re-run the report-only review with the same criteria.

Gate 3 · Sign off the review

No known release blockers remain in the reviewed build. Prepare
release-readiness materials only; do not publish.

04 Publish readiness Same project session

Prompt 4 · Prepare release readiness

@github-skills-orchestrator Use /github-skills-publish for the
approved three-step exercise. Read its identity from
.github/exercise-outline.md.

Prepare a short readiness report: validation evidence, untested risks, a PR
description, brief release notes, and a launch checklist. Clearly separate
completed checks from required fresh-copy testing.

Do not create or transfer repositories, change visibility, push, or publish.
Stop at the authorization boundary.

Prompt 4b · Show the publish plan, without authorizing it

Use /github-skills-publish to show, without executing, a plan for
publishing this exercise to <demo-owner>/<approved-name> as a public template.

Show the exact target, visibility, changes, commands, and readiness blockers.
Wait for separate explicit authorization. This message is not authorization to
create, push, transfer, change settings, or publish.

05 The whole loop Shown, not run on stage

Orchestrate every phase with the same gates

@github-skills-orchestrator Use /github-skills-orchestrate to
coordinate the same three-step Tailspin quick-start. Read the approved outline
from .github/exercise-outline.md. Stop after each build for approval; review
without edits; request separate approval for fixes and any publication. Do not
expand the scope or publish without explicit authorization.

The hand-off script

Moves the approved outline from a quick chat into a real repository.

  1. Creates <owner>/<name> as a private repository with gh and clones it under parent-dir (default ~/src/workshop-demo).
  2. Imports a shallow copy of Tailspin Toys as one MIT-licensed starter commit, leaving out its upstream issue seeding, maintainer triage workflow, and CODEOWNERS.
  3. Pushes main.

--dry-run builds the same commit locally without creating or pushing anything on GitHub. It still clones Tailspin, so it needs a network connection. The script requires an authenticated gh, git, and rsync.

Download

handoff.sh

Make it executable, then try a dry run

chmod +x handoff.sh
./handoff.sh --dry-run <you> copilot-app-cleared-for-takeoff
